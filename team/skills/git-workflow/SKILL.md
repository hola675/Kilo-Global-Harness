# Git: mínima divergencia, integración y conservación

## Responsabilidad y alcance
Code controla base, decisiones de integración, propietario de índice/refs y aceptación; especialistas escriben solo alcance asignado y entregan evidencia. Forja puede aportar análisis de CI/distribución; Veritas contrasta garantías sin mutar objeto. Respetar AGENTS.md, reglas del repositorio, protección efectiva y autorización vigente. No asumir permiso de publicar, eliminar, cambiar protección, credenciales o historial. Team-coordination controla ejecución y propiedad; focused-testing certifica garantías y vigencia de evidencia; esta skill gobierna identidad y operaciones Git. No depende de otras skills, herramientas nuevas ni hosting particular.

## 1. Identificar repositorio y proteger estado
Antes de mutar confirmar raíz, Git dir/common dir cuando importe, rama o HEAD detached, revisión, upstream/base y remoto correctos, alcance y operación en progreso (merge/rebase/cherry-pick/bisect). Diferenciar submódulo de worktree vinculado, workspace local de entorno administrado y Git remoto de copia de trabajo local: consultar solo repositorio autorizado, no credenciales. Inspeccionar estado, cambios staged/unstaged/no rastreados relevantes, divergencia y escritores activos. Un diff vacío no acredita ausencia de archivos ignorados/no rastreados ni operaciones remotas; no afirmar limpieza de un clon no observado. Preservar cambios previos y de terceros, incluidos index y archivos generados. No reset --hard, clean, restore masivo, checkout destructivo, stash automático, force-push ni borrar trabajo para habilitar operación. Si estado no permite mutar sin riesgo, limitar operación, coordinar con dueño o pedir autorización material. Usar comandos de lectura apropiados a plataforma y versión, inspeccionar efectos (hooks, filtros, submódulos, red) antes de operaciones de escritura.
Para repositorios sin Git o sin remoto, no inicializar, clonar, publicar ni inventar rama por rutina. En revisión remota por API usar identidad repositorio/ref/head; no prometer efecto en PC local. Ante fallo, resultado incierto o concurrencia, volver a leer estado pertinente antes de reintentar.

## 2. Ramas mínimas y trabajo simultáneo
Por defecto una rama principal estable (main o nombre vigente) y una temporal propia por conjunto coherente de trabajo. Máximo tres ramas propias de trabajo incluyendo principal: tercera excepcional por aislamiento real, hotfix incompatible o necesidad demostrada, sin romper política del proyecto. No rama por especialista, prueba, commit ni fase si una rama activa sirve. Respetar ramas de release, protección y ramas de terceros impuestas por repositorio; no computar límite como autorización de eliminarlas. Registrar discrepancia si excede límite por historia o dependencias ajenas; no aumentar divergencia. Antes de abrir otra línea de trabajo consolidar resultado anterior aceptado o continuar su rama; si falta revisión/permiso, conservarla y bloquear nueva rama, no forzar merge. Una rama temporal con PR borrador puede contener incrementos dependientes, siempre que la puerta del conjunto permanezca explícita y no se altere revisión aprobada sin reevaluar. No crear rama/PR por rutina para tarea de solo lectura.
Compartir rama solo con alcance de escritura disjunto y recursos compatibles; índice, refs, cambio de rama y merge tienen un escritor coordinado. El límite de ramas no es límite de especialistas concurrentes. Worktree solo cuando se necesita aislamiento de archivos/índice y está autorizado; preferir capacidad nativa verificada si existe, comprobar propietario, ruta, base y ramas ocupadas. No anidar worktrees, cambiar rama bajo escritores activos, usar --force para checkout ocupado ni asumir que un worktree aísla refs, servicios, puertos o secretos. No instalar dependencias ni modificar .gitignore automáticamente. Si aislamiento no disponible, secuenciar operaciones incompatibles.

## 3. Commit y sincronización controlados
Seleccionar cambios propios por rutas/hunks exactos, incluyendo eliminaciones autorizadas; inspeccionar diff staged completo antes del commit. Evitar git add . / -A indiscriminados, staging de secretos, artefactos locales o cambios de otros. Si índice contiene cambios ajenos, no apropiarlos ni deshacerlos; coordinar propietario o aislar con mecanismo autorizado. Mantener incremento autocontenido con pruebas/metadata/changelog pertinentes; mensaje claro según convención, idioma y alcance. No crear commits vacíos, informes repetitivos ni reescribir commits publicados por estética. Un commit candidato puede existir con validación pendiente, declarada en mensaje/PR/retorno; no equivale a versión certificada. Versionar archivos individualmente según reglas vigentes; release independiente de esos números.
Consultar base/remoto vigente antes de sincronizar; fetch autorizado no equivale a merge. Preferir fast-forward-only cuando se espera actualización lineal; si divergencia real, inspeccionar cambios, no pull ambiguo ni rebase automático de historial compartido. Elegir integración según política y revisión, preservando cambios y semántica. Resolver conflictos en alcance con dueño, comprender ambos lados y contratos; no elegir ours/theirs globalmente ni resolver a ciegas locks, migraciones o marcador. Validar resultado integrado; si conflicto no resoluble, conservar estado, informar y no abortar operación ajena. Push solo remoto/ref autorizado, sin force-push, comprobar rechazo o carrera y reconciliar resultado. Cuando API soporte actualización condicional por head esperado, utilizarla; no inventar garantía atómica si herramienta no la ofrece.

## 4. Integración, publicación y cierre
Identificar destino, base y head exactos, diff, aprobaciones, estado draft, checks requeridos y reglas efectivas (incluidas rulesets, no solo flag protected). Verificar criterios y revisión independiente según riesgo, no confundir mergeable con aprobado ni green anterior con revisión vigente. Reutilizar evidencia por criterio solo si válida; comprobar resultado de integración y respetar checks obligatorios de revisión requerida. Si head/base cambian, reevaluar delta y aprobación vigente; no integrar objeto distinto al revisado. No publicar, fusionar ni crear tags/releases fuera de autorización; no cerrar PR pendiente por conveniencia ni eliminar protección para evitar bloqueo.
Elegir merge, squash o rebase según convenciones, trazabilidad y alcance aprobado; no imponer método. Squash/rebase pueden cambiar identidad de commits: evidencia de integración no depende solo de ancestro. Tras merge, confirmar destino real, estado PR, revisión resultante y presencia semántica del cambio; si verificación final falla, preservar rama/evidencia, comunicar incidente y corregir mediante nuevo cambio autorizado. Revertir commit compartido con nuevo commit cuando autorizado, no reescribir historia ni prometer reversión de datos por Git. Para release comprobar artefactos, versión, puertas y autorización por separado.

## 5. Consolidación y limpieza
Inventariar ramas locales/remotas reales y worktrees pertinentes; clasificar principal/protegida, activa, integrada, dependida, única/no integrada o incierta. Comprobar PR asociado y head final, inclusión por ancestros o equivalencia de contenido/patch y destino actual cuando hubo squash/rebase; un PR cerrado, antigüedad, nombre temporal o fecha no demuestra integración. No confundir eliminación local, remoto, tracking y registro worktree. Antes de retirar, comprobar escritores, worktrees, cambios sin commit, commits únicos, PR dependientes, referencias de evidencia y autorización aplicable. Si alguna condición incierta, conservar y reportar. No borrar ramas ajenas ni usar eliminación masiva/forzada para cumplir límite; si Git rechaza eliminación segura por squash, demostrar inclusión y obtener autorización específica para método excepcional, o conservar. Nunca aplicar force-delete genérico ni prune destructivo a espacios administrados. Limpiar solo ramas/worktrees propios integrados y autorizados, verificando estado posterior. Si no existe capacidad de retirada, informar inventario y plan/manual seguro; no simular limpieza.
Para marcador quality-baseline, conservar historial y revisión/inputs reales inspeccionados. No cambiar audited_revision al nuevo commit por mera integración, no reescribir JSON por cada commit. Tras merge/squash/rebase verificar identidad, contenido de inputs y garantías afectadas; recuperar evidencia por objeto equivalente cuando demostrable y revalidar ámbitos desactualizados. Resolver conflicto de marcador por evidencia/alcance, no por fecha o COMPLETE más reciente. No convertir marcador en check PASS ni omitir CI. No crear tag para auditoría.
Entregar a Code/usuario: rama/base/head, cambios propios, estado local/remoto observado, pruebas/revisión vigentes o pendientes, PR/merge y limpieza realmente ejecutados, bloqueos y siguiente acción concreta. Distinguir commit, push, merge, release y despliegue. No afirmar consolidación si permanecen ramas pendientes o no se observó estado local.
