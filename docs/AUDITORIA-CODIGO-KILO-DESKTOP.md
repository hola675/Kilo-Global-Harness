## 1. Capas y arranque
Electron/React, kernel principal y uno por ventana, plugins con contratos Zod, IPC validado. kilo.work-sessions posee workspaces/work sessions (directorios o worktrees y panes); una work session contiene varios chats; cada chat equivale a sesión del agente CLI. kilo.core administra conexión, configuración, procesos y tools; kilo.chat renderiza conversaciones, colas y subagentes. KiloServerManager inicia kilo serve local, verifica health y versión fijada (salvo instalación personalizada), controla reinicio. No crear otro motor ni servidor por cada agente.

## 2. Configuración y precedencia: hallazgo crítico
Desktop fuerza KILO_CONFIG_DIR a su directorio administrado <storage de kilo.core>/agent/runtime/config/kilo y usa XDG_STATE_HOME propio salvo override heredado. Mantiene XDG_CONFIG_HOME heredado si existe. El config global del usuario NO es necesariamente el config administrado de Desktop. Este último mantiene sidecar de propiedad y reconciliación por fuente de agentes, comandos, MCP, plugins y skills; cambios pueden solicitar reinicio del servidor. No editar sidecar ni config administrado directamente.
El motor carga configuración global, configuración explícita, archivos de proyecto kilo/opencode, directorios (incluidas configuraciones de checkout principal como fallback para worktrees), perfil KILO_CONFIG_DIR y contenido inline; reglas específicas de merge impiden inferir precedencia absoluta de todos los campos. Para AGENTS.md global elige el PRIMER archivo existente: perfil KILO_CONFIG_DIR/AGENTS.md, global.config/AGENTS.md, luego CLAUDE.md global si permitido y no migrado. En proyecto busca AGENTS.md, CLAUDE.md (si habilitado), CONTEXT.md, priorizando primer tipo con matches. Config instructions agrega fuentes. Por tanto copiar AGENTS.md global a cualquier ruta no garantiza activación; probar con marcador benigno, detectar shadowing y no sobrescribir el perfil Desktop.
Skills: .agents/.claude de usuario/proyecto según flags, directorios de configuración skill/skills, rutas extra y URLs; skills incorporadas se cargan primero y pueden ser sobreescritas por descubrimiento; nombres duplicados generan aviso. No instalar duplicados. Markdown de proyecto no recibe automáticamente confianza global.

## 3. Code, agentes y procesamiento
El motor construye build, plan, general y explore entre otros, renombra build a code para compatibilidad y procesa configuración por agente. Code es default preferido si visible y no se configura otro default válido; general y explore son subagentes nativos. Los especialistas deben usar mode: subagent; no crear modo primario duplicado. El motor expone a task los agentes no primarios que no estén denegados; la selección es del modelo, no scheduler determinista de competencias.
Flujo: renderer crea chat mediante work-sessions, usa SDK por directorio y stream de eventos, mantiene cola de prompts en main, no confundir cola de usuario con DAG. Motor session/prompt construye contexto de entorno, memoria, instrucciones, MCP, catálogo skills y board cuando corresponde; convierte historial en mensajes, resuelve agente y herramientas, procesa el modelo, ejecuta llamadas, actualiza estado y compacta al necesitarlo. Hooks tool.execute.before/after están implementados; no asumir que un plugin propio se carga en Desktop sin probarlo.

## 4. Task, concurrencia y Swarm
Task recibe description, prompt, subagent_type, task_id opcional, command opcional y campos opcionales de modelo; background aparece en schema cuando flag habilitado (default true en esta versión). El task crea sesión hija con parentID, registra ancestry, aplica permisos, ejecuta prompt. Foreground espera resultado; background devuelve identificador, puede aceptar contexto adicional y notifica resultado a padre de forma nativa; no polling ni sleeps. task_id solo reanuda una hija de la sesión actual; no cross-session resume. El límite subagent_depth por defecto es 1 (hijos directos); nesting requiere aumentar límite y permisos efectivos. No cambiarlo hasta medir necesidad. No se ha demostrado un límite general de concurrencia; no inventar número máximo del motor. Selección de modelo considera workflow, modelo guardado, agente, subagent_model, fallback a padre; parámetros de override dinámico solo cuando usuario los solicita, según descripción nativa. Evitar asignación dinámica arbitraria de modelos.
Board habilitado por defecto; opt-out config shared_agent_board:false o flag falso. board_post y board_read en árbol de sesión raíz; lectura incremental con cursor; mensajes almacenados no prueban lectura, no despiertan agentes ni son locks. Code sigue trabajo no superpuesto; ownership de archivos y dependencias siguen siendo responsabilidad del equipo.
Desktop muestra árbol de sesiones hijo, permisos/preguntas pendientes y estado de ejecución; el código distingue tarea background retornada de hijo activo. Etiqueta UI done no acredita aceptación funcional. Work sessions independientes no equivalen a Task hijas ni a un Swarm común.

## 5. Permisos y seguridad
No es herencia total de permisos del líder: reglas por agente, reglas de sesión padre (deny y external_directory), techos de mutación/MCP/board y restricciones task/todowrite/question/suggest, según ruta de creación/reanudación. Permisos de shell no equivalen a confinamiento de filesystem. Desktop construye reglas por chat: carpetas workspace, contribuciones, ask y deny al final; último match en ese ruleset. Código inspeccionado estampa kilocode.sandbox enabled:false para nuevos chats porque Desktop no tiene setting propio todavía. No presentar worktrees, prompt, renderer sandbox o permisos de herramienta como sandbox de ejecución. Verificar estado instalado. Separar permisos de operación, alcance y aislamiento técnico. Probar denegaciones efectivas, no solo schema.

## 6. MCP y dos sistemas de plugins
Plugins Desktop (kernel, main/web, plugin.json y extensión kilo.core/tool) son diferentes de plugins del motor CLI (hooks, config). Desktop aporta tools mediante gateway MCP interno a kilo serve; nombres desktop_*, autenticación por arranque, contexto de chat/work session, aprobación por reglas, sin utilizar herramientas de otra sesión enfocada por error. No reutilizar tokens internos, exponer endpoints ni modificar ASAR. Las herramientas de apps externas son otra interfaz opt-in, no equivalen a extensibilidad del agente, sin contexto de chat. Marketplace usa API del CLI para catálogo/instalar/remover por alcance. No asumir soporte de carga de plugins Desktop externos ni confundirlo con plugins CLI. Para Harness: usar config, skills, agentes y MCP estándar; plugin motor solo si brecha demostrada; plugin Desktop solo si feature de UI necesaria y carga soportada.

## 7. Decisiones de diseño a incorporar en F02/F03
- Identificar versión de binario empaquetado, no confiar en kilo del PATH; registrar versión y hash sin argumentos ni secretos.
- Resolver config global y perfil Desktop separados, presencia y hash de AGENTS.md, duplicados de agentes/skills y fallbacks de checkout principal. Probar cuál llega a un chat nuevo, sin escribir configs de usuario.
- Probar Code sin modificar prompt; subagente mínimo mode:subagent, task y skill reales; validar exposición background/board y resultados, dos hijos con timestamps y alcance no superpuesto.
- Mantener subagent_depth=1 inicialmente; ampliar solo ante caso probado, no dar task a todos automáticamente.
- Validar permisos por rol y sesión, MCP visible e invocable, y aislamiento real; no atribuir sandbox a Desktop.
- Aprovechar estado, eventos, cola, sesiones y árbol de hijos existentes; no crear observer técnico, scheduler o MCP de estado antes de verificar brecha.
- Modelos: respetar selección nativa/config autorizada, no elegir overrides autónomos por coste.
- Certificar recuperación de task_id dentro de sesión, cancelación, reinicio y compactación por separado. No asumir persistencia de trabajos activos tras cerrar app.
- Mantener Team Learning como metaskill de Code y no segundo líder.

Estado: F02 runtime sigue pendiente; sin compilación ni ejecución de Desktop/CLI, ni pruebas en Windows. No se modifica upstream ni legacy. Las conclusiones de código son de snapshots fijados, no afirmaciones sobre releases posteriores.
