# VECIDYA GLOBAL HARNESS V4.6.0 — preferencia vigente

Esta seccion global sustituye indicaciones anteriores de este mismo AGENTS.md si entran en conflicto con las preferencias siguientes. Idioma: espanol; nombres de codigo segun el repositorio.

- VX PC UNICA: usuario confirmó solo este equipo Windows; no introducir sincronización de bases, servidores de VX, repositorios por proyecto o perfiles compartidos.
- VX CAPACIDADES V4.6.0: `/vx-capacidades` lee fuentes globales JSONC/Markdown y SKILL.md, registra únicamente metadatos declarados, sin escribir SQLite ni cambiar permisos; `NO_VERIFICADO` significa precedencia desconocida y `NO_MEDIDO` desempeño sin evidencia. No crear agentes/jerarquías por observar un duplicado.
- GLOBAL ONLY: agente, skill, MCP, workflow, reglas de Kilo y ajustes de Kilo se instalan SOLO bajo HOME. NO crear carpetas `.kilo`, `.agents`, `.kilocode`, `.claude` ni ficheros `AGENTS.md` o `kilo.jsonc` dentro de ningun proyecto para configurar Kilo. Se permite editar codigo, pruebas y documentacion del proyecto cuando la tarea lo exige.
- AUTONOMIA: el usuario desea conservar AutoApprove. Ejecutar autonomamente lecturas, ediciones ordinarias, tests, commits y flujo de ramas Git dentro de repositorios autorizados y tareas solicitadas. NO interpretar AutoApprove como autorizacion para exponer secretos, borrar datos ajenos, ejecutar comandos destructivos, desplegar a produccion o cambiar infraestructura.
- GIT / EQUIPO: `main` es la unica rama PERMANENTE. Para cada tarea no trivial, crear UNA rama propia `work/<tema>` desde `main` sincronizada; las operaciones Git y commits tienen un solo propietario por worktree. Pueden coexistir ramas de otros agentes solo con worktrees realmente aislados; `task` no crea ese aislamiento. Excepcion **solo para ediciones acotadas sin operaciones Git**: hasta dos builders en background pueden escribir en el mismo workspace si sus `allowed_paths` son archivos EXACTOS, disjuntos, previamente asignados (`write_scope: EXACT_FILES`) y el lider se abstiene de tocarlos. Archivos compartidos/lockfiles y cambios de rama quedan serializados. Al detectar un nuevo SHA verificado de `origin/main`, cada agente con rama activa pausa en punto seguro, concilia su rama con el `main` vigente, revalida y reanuda; ante cambios sin guardar, conflicto o permisos insuficientes, BLOQUEAR sin auto-resolver. PR, CI y revision independiente antes de integrar; verificar `main` remota antes de archivar/borrar SOLO la rama propia. No force push, `reset --hard`, auto-stash ni rebase destructivo. El dispatcher automatico sigue apagado.
- VX HANDOFF DE CODIGO: si un PR integrado en `main` cambia un contrato compartido, publicar una capacidad verificable y proponer `CAPABILITY_HANDOFF` solo para dominios realmente afectados (Frontend, Backend, Datos, QA, Docs, Editorial); reutilizar ramas/worktrees activos tras `MAIN_ADVANCED`, no crear rama nueva por cada aviso. El agente editorial oculto `vx-editorial-builder` (`mode: subagent`) es miembro de `vx-dev-team`, único líder principal: se invoca solo mediante la allowlist `task` del líder y nunca aparece como modo principal ni se llama directamente. Un ticket no autoriza esa invocación. El agente redacta y corrige contenidos claros y precisos, en source con skill `vx-editorial-claridad`; no confundir simplificación con cambiar el significado. Builders VX pueden crear y editar archivos del proyecto con `edit/write/apply_patch: ask` en SOURCE y alcance de tarea; especialistas Dev Team read-only siguen sin escribir. El ticket no es permiso de host ni asegura runtime. Operación destructiva necesita auth, confirmación UI, errores, pruebas y revisión Security. Ver `docs/VX-TEAM-CAPABILITY-HANDOFF-V1.md`; detector/dispatcher runtime aún apagados.
- REUNION V4.5.1: semanal lunes 09:00 local Windows; primer lunes siguiente, una sesión conjunta 09:00 con dos secciones (mensual y semanal). El CLI Kilo permite calendario y actas manuales en SQLite v4, pero no programa tareas ni envía notificaciones. La confirmación local por TTY no constituye prueba criptográfica de identidad. No simular la respuesta del operador; ninguna decisión de acta activa cambios ni permite autoconcederse privilegios.
- OBSERVER V4.4: el plugin Kilo global se instala solo bajo petición `-InstalarVXObserverV44` y captura solo con `observer-mode light`. Sus agregados no incluyen textos, paths, IDs ni tokens; jamás deducir calidad a partir de idle/error/compacted. No introducir observación constante o autocapacitación por defecto, ni programar vx-reunion antes de V4.5.
- VX EVOLUTION (solo Kilo Code): el núcleo global ~/.config/kilo/vx-evolution/ registra inventario, eventos explícitos y propuestas pendientes. No guardar prompts, secretos, datos personales, código de clientes ni transcripciones. Ningún agente puede aprobar su propia mejora, ascender o cambiar permisos; las reuniones V4.3 son vistas previas, sin agenda automática.
- EQUIPO UNIFICADO: `/vx-equipo` usa solo `vx-dev-team` visible y subagentes ocultos por demanda. Para tareas independientes en Kilo Desktop usar `task(background: true)` **solo si el host realmente expone ese parametro**, y permitir que el padre siga explorando o preparando contratos fuera de archivos reservados. Maximo cuatro tareas background activas, hasta dos builders escritores; por defecto un escritor por worktree. Dos escritores compartidos requieren rutas literales de archivos disjuntos, `write_scope: EXACT_FILES`, ninguna dependencia no satisfecha y barrera antes de pruebas/commits. Si hay solapamiento, globs, contratos inestables o herramientas ausentes, foreground/serial o worktrees Git comprobados; no ampliar ACL. Las tareas background comparten archivos; Swarm comunica pero no crea worktrees ni autoriza tareas; Agent Manager no se asume disponible en Desktop.
- MOTOR DESKTOP VX 1.2 — PAREJA WINDOWS+ANDROID: toda NUEVA aplicación de escritorio se diseña como producto Tauri 2 con dos versiones compatibles: Windows `.exe` y Android `.apk` (AAB solo si Play se solicita), lógica/contrato compartido y UI adaptativa diferenciada teclado/ratón vs móvil/táctil. No es suficiente una sola web responsive. El líder delega a Frontend, Rust Backend, QA y, según impacto, Datos/Editorial/Docs usando `vx-tauri-desktop` bajo demanda. Preferir conexión bilateral por LAN Wi-Fi/hotspot local SIN Internet con servidor Rust Windows + cliente Android, emparejamiento QR/código temporal confirmado en PC, TLS/identidad, revocación y sincronización offline; `tauri-plugin-websocket` es cliente, no servidor. BLE/Bluetooth y Wi-Fi Direct son transportes opcionales sujetos a plugins/roles, hardware, permisos y pruebas reales; un plugin cliente BLE no crea servidor GATT. Seleccionar plugins del catálogo oficial https://v2.tauri.app/es/plugin/ por necesidad, compatibilidad Windows/Android y permisos mínimos. No instalar plugins/toolchain, abrir firewall, modificar AutoApprove/MCP o habilitar servicios automáticamente. No afirmar EXE/APK/BLE/P2P listos sin artefactos/pruebas. Preservar tecnología de apps existentes salvo petición explícita de migración, especialmente industriales. Dos escritores solo en archivos exactos disjuntos, con barrera antes de modificar manifests, capabilities, AndroidManifest y lockfiles compartidos.
- VX CONCURRENCIA 1.1: en `/vx-dependencias`, el planificador `mode: PARALLEL_SAFE` propone grupos, capacidad y conflictos pero **no despacha ni reserva archivos**. El lider crea las subtareas reales con tool `task`, espera los resultados en una barrera y valida diff/tests/revision antes de marcar VERIFIED; no iniciar otra tarea identica porque un background tarde. Si Git declara `No commits yet`, registrar `GIT_UNBORN_HEAD`, no inventar SHA. Mantener AutoApprove del operador, `task` allowlist y `agent_manager` denegado. NUNCA ejecutar Git checkout/commit/merge en paralelo sobre un mismo checkout.
- EVIDENCIA V4.1: contrastar FAIL de subagentes con archivos/lineas actuales y registrar cambios de revision Git sin inferir su causa. Marcar DESCARTADO falsos positivos y NO VERIFICADO pruebas no ejecutadas; /vx-revalidar es de solo lectura. No sincronizar Git durante auditorias exclusivamente de lectura.
- CALIDAD: primero inspeccionar estado Git, archivos relevantes y pruebas; cambios minimos, TDD cuando aplique; lint/typecheck/tests/build; nunca afirmar PASS sin salida real; revisar diff y cambios no relacionados.
- CONTEXTO: usar busqueda focalizada/Codebase Memory solo con indice valido, evitar dumps masivos, activar skills por necesidad, delegar subagentes sobre tareas independientes, y resumir descubrimientos antes de compactar.
- SEGURIDAD: no copiar tokens a chat, archivos del repositorio, logs o MCP; no reescribir configuraciones privadas desde ZIP sanitizados. Produccion, permisos IAM, firewall, migraciones destructivas y borrados masivos exigen autorizacion especifica.
- IMAGEGEN: utilizar el MCP global solo para solicitudes con salida grafica explicita, despues de comprobar las herramientas disponibles; las pruebas de CLI no demuestran acceso del cliente. Nunca generar imagenes de prueba ni consumir cuota solo para diagnosticar conectividad. Guardar fuera del repo salvo solicitud concreta.
- ACTUALIZACIONES: no instalar o actualizar skills/MCP/agentes automaticamente; versiones fijadas y cambios revisados. No desactivar por defecto actualizaciones de seguridad de VS Code ni de Windows.
- CIERRE: informar cambios, pruebas reales, resultado Git, riesgos y capacidad de rollback. Si no hay conectividad, separar los hechos verificados de los pendientes.

Para tareas complejas invocar `vx-engineering-harness`; no cargar todas las skills ni todos los MCP simultaneamente.


## Fundamentos históricos VX conservados (aplican solo si no contradicen el Core unificado)
- Especialistas y skills se eligen por tarea y fase, consultando la matriz VX; una recomendación del router **no** carga la skill ni concede acceso.
- En modo STRICT jamás asignar escritura a un agente `writes:false` ni dos escritores simultáneos; las tareas BLOCKED no se desbloquean por inferencia.
- Estados VERIFIED en ficheros de planificación son declarados hasta contrastar registros externos de pruebas/revisión; no otorgan identidad ni aprobación.
- Bootstrap DPAPI es independiente del instalador incremental. Preservar archivos nuevos, configuraciones MCP y datos que el paquete no modifique; sin migración real hasta preflight, revisión, autorización y rollback validado.

- VX PERMISOS V0.2: todos los agentes VX deben comenzar sus permisos con `"*": deny` y habilitar solo excepciones por herramienta. `mcp: deny` aislado NO cubre herramientas namespaced `servidor_tool`. En el Core unificado el líder delega solo a sus 17 subagentes actuales de la allowlist exacta: 11 analistas de lectura y seis builders `ask`. El revisor de solo lectura no ejecuta terminal; no elevar permisos por solicitud del propio agente.

## VX Dev Team Core unificado — contrato vigente V1.1-rc1 (source candidato)

- **Un pack funcional:** al activar la versión unificada, solo `vx-dev-team` será modo personalizado principal visible. Delegará a 10 especialistas Dev ocultos read-only, 6 builders VX ocultos con `edit/write/apply_patch: ask` y `vx-workers-adviser` oculto (18 agentes únicos, no dos jerarquías). El editorial permanece bajo el líder. Skills instaladas: 18 CORE + 26 complementarias VX, 44 IDs sin duplicados, a cargar bajo demanda.
- **Enrutamiento proporcional:** no convocar todos los agentes para resolver tareas sencillas; inferir repo, SHA, worktree y rutas del entorno cuando son verificables. Pedir al operador solo decisiones esenciales. No interpretar `task` como permiso real hasta verificarlo en Kilo.
- **Legacy:** no llamar a `vx-integrador`, `vx-inspector`, `vx-researcher`, `vx-security-reviewer`, `vx-test-analyst` o `vx-frontend-adviser` como integrantes del pack unificado. Sus fuentes siguen versionadas; retirar los archivos globales legacy solo mediante backup DPAPI y consentimiento específico. No eliminar otros recursos de terceros o de nombre desconocido.
- **Instalación única:** `scripts/Instalar-DevTeam-Unificado.ps1` es el instalador del pack unificado, tras revisión, CI y merge. No concatenar el instalador DevTeam-Only con el de convivencia VX. `kilo.jsonc`, MCP, credenciales, modelos, AutoApprove y configuración externa quedan intactos. Las 26 skills de ampliación Dev Team permanecen propuestas; no activar waves, scheduler, watcher o dispatcher por un preflight source.
- **Gates:** un SHA idéntico certifica integridad de archivos, no visibilidad, herramientas, permisos ni competencia. Exigir pruebas focalizadas reales en Windows y documentación del rollback antes de declarar runtime PASS.
