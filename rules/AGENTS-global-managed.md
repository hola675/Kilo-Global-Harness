# VECIDYA GLOBAL HARNESS V4.6.0 — preferencia vigente

Esta seccion global sustituye indicaciones anteriores de este mismo AGENTS.md si entran en conflicto con las preferencias siguientes. Idioma: espanol; nombres de codigo segun el repositorio.

- VX PC UNICA: usuario confirmó solo este equipo Windows; no introducir sincronización de bases, servidores de VX, repositorios por proyecto o perfiles compartidos.
- VX CAPACIDADES V4.6.0: `/vx-capacidades` lee fuentes globales JSONC/Markdown y SKILL.md, registra únicamente metadatos declarados, sin escribir SQLite ni cambiar permisos; `NO_VERIFICADO` significa precedencia desconocida y `NO_MEDIDO` desempeño sin evidencia. No crear agentes/jerarquías por observar un duplicado.
- GLOBAL ONLY: agente, skill, MCP, workflow, reglas de Kilo y ajustes de Kilo se instalan SOLO bajo HOME. NO crear carpetas `.kilo`, `.agents`, `.kilocode`, `.claude` ni ficheros `AGENTS.md` o `kilo.jsonc` dentro de ningun proyecto para configurar Kilo. Se permite editar codigo, pruebas y documentacion del proyecto cuando la tarea lo exige.
- AUTONOMIA: el usuario desea conservar AutoApprove. Ejecutar autonomamente lecturas, ediciones ordinarias, tests, commits y flujo de ramas Git dentro de repositorios autorizados y tareas solicitadas. NO interpretar AutoApprove como autorizacion para exponer secretos, borrar datos ajenos, ejecutar comandos destructivos, desplegar a produccion o cambiar infraestructura.
- GIT / EQUIPO: `main` es la unica rama PERMANENTE. Para cada tarea no trivial, crear UNA rama propia `work/<tema>` desde `main` sincronizada; pueden coexistir ramas de otros agentes solo con propietarios/worktrees aislados y un escritor por worktree. Al detectar un nuevo SHA verificado de `origin/main`, cada agente con rama activa pausa en un punto seguro, concilia su rama con el `main` vigente, revalida y reanuda; si hay cambios sin guardar, conflicto o permisos insuficientes, BLOQUEAR sin auto-resolver. Integrar mediante PR, CI y revision independiente; verificar `main` remota antes de archivar/borrar SOLO la rama propia. No usar force push, `reset --hard`, auto-stash ni rebase destructivo de ramas compartidas. El detector/dispatcher automatico todavia NO esta activo: ver `docs/VX-TEAM-GIT-RECONCILIATION-V1.md`. No se amplian ACL.
- VX HANDOFF DE CODIGO: si un PR integrado en `main` cambia un contrato compartido, publicar una capacidad verificable y proponer `CAPABILITY_HANDOFF` solo para dominios realmente afectados (Frontend, Backend, Data, QA, Docs); reutilizar ramas/worktrees activos tras `MAIN_ADVANCED`, no crear rama nueva por cada aviso. Builders VX pueden crear y editar archivos del proyecto con `edit/write/apply_patch: ask` en SOURCE y alcance de tarea; especialistas Dev Team read-only siguen sin escribir. El ticket no es permiso de host ni asegura runtime. Operación destructiva necesita auth, confirmación UI, errores, pruebas y revisión Security. Ver `docs/VX-TEAM-CAPABILITY-HANDOFF-V1.md`; detector/dispatcher runtime aún apagados.
- REUNION V4.5.1: semanal lunes 09:00 local Windows; primer lunes siguiente, una sesión conjunta 09:00 con dos secciones (mensual y semanal). El CLI Kilo permite calendario y actas manuales en SQLite v4, pero no programa tareas ni envía notificaciones. La confirmación local por TTY no constituye prueba criptográfica de identidad. No simular la respuesta del operador; ninguna decisión de acta activa cambios ni permite autoconcederse privilegios.
- OBSERVER V4.4: el plugin Kilo global se instala solo bajo petición `-InstalarVXObserverV44` y captura solo con `observer-mode light`. Sus agregados no incluyen textos, paths, IDs ni tokens; jamás deducir calidad a partir de idle/error/compacted. No introducir observación constante o autocapacitación por defecto, ni programar vx-reunion antes de V4.5.
- VX EVOLUTION (solo Kilo Code): el núcleo global ~/.config/kilo/vx-evolution/ registra inventario, eventos explícitos y propuestas pendientes. No guardar prompts, secretos, datos personales, código de clientes ni transcripciones. Ningún agente puede aprobar su propia mejora, ascender o cambiar permisos; las reuniones V4.3 son vistas previas, sin agenda automática.
- EQUIPOS V4: usar /vx-equipo y el registro global cuando la tarea requiera especializacion. Maximo tres lectores independientes concurrentes y UN solo escritor. task(background) comparte archivos; Kilo Swarm solo comunica, no programa ni autoriza tareas. El modo avanzado de edicion en worktrees separados exige permiso especifico.
- EVIDENCIA V4.1: contrastar FAIL de subagentes con archivos/lineas actuales y registrar cambios de revision Git sin inferir su causa. Marcar DESCARTADO falsos positivos y NO VERIFICADO pruebas no ejecutadas; /vx-revalidar es de solo lectura. No sincronizar Git durante auditorias exclusivamente de lectura.
- CALIDAD: primero inspeccionar estado Git, archivos relevantes y pruebas; cambios minimos, TDD cuando aplique; lint/typecheck/tests/build; nunca afirmar PASS sin salida real; revisar diff y cambios no relacionados.
- CONTEXTO: usar busqueda focalizada/Codebase Memory solo con indice valido, evitar dumps masivos, activar skills por necesidad, delegar subagentes sobre tareas independientes, y resumir descubrimientos antes de compactar.
- SEGURIDAD: no copiar tokens a chat, archivos del repositorio, logs o MCP; no reescribir configuraciones privadas desde ZIP sanitizados. Produccion, permisos IAM, firewall, migraciones destructivas y borrados masivos exigen autorizacion especifica.
- IMAGEGEN: utilizar el MCP global solo para solicitudes con salida grafica explicita, despues de comprobar las herramientas disponibles; las pruebas de CLI no demuestran acceso del cliente. Nunca generar imagenes de prueba ni consumir cuota solo para diagnosticar conectividad. Guardar fuera del repo salvo solicitud concreta.
- ACTUALIZACIONES: no instalar o actualizar skills/MCP/agentes automaticamente; versiones fijadas y cambios revisados. No desactivar por defecto actualizaciones de seguridad de VS Code ni de Windows.
- CIERRE: informar cambios, pruebas reales, resultado Git, riesgos y capacidad de rollback. Si no hay conectividad, separar los hechos verificados de los pendientes.

Para tareas complejas invocar `vx-engineering-harness`; no cargar todas las skills ni todos los MCP simultaneamente.
